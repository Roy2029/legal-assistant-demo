## 1. 目标与边界

### 1.1 目标

定义**离线索引构建管线**的完整设计：从原始法规 / 用户文档，到 Qdrant 中可检索的 child/parent 双层索引。

### 1.2 范围

**包含**：解析、结构预处理、递归分块、父子索引、嵌入与索引构建、元数据、增量更新、用户知识库复用。

**不包含**：在线检索与 rerank（D02）、PreFilter 与查询端路由（D02）、实务 skill（D06）、可观测性（D03）。

## 3. 模块设计

### 3.1 解析管线

**输入格式**：md / txt / docx / pdf（用户库）；国家法律库 docx（公共库）。

**流程**：

```
docx ──python-docx（首选：段落/标题层级/表格/样式保真）──> plaintext + 结构信息
     └─失败降级──> Markitdown 转 md
pdf  ──Markitdown 转 md（首选）──> plaintext
     └─失败/质量不足降级──> PyMuPDF 文本层提取
md/txt ──直接解析──> plaintext + 结构信息
扫描件（文本 < 50 字符/页）──> M0 拒绝并提示
```

**输出**：`plaintext + 结构信息`（标题层级、段落、表格、图片占位、时效描述、目录）。

**特殊内容处理（已确认）**：

| 内容 | 处理 |
|------|------|
| 目录 | M0 不作结构化导航，作为正文参与分块；若检索命中目录页，由生成端忽略（D02 约束） |
| 序言 | 按普通章节处理，结构路径标"序言" |
| 书名号引文 | 分句时不在书名号中间切分；解析阶段提取被引法规名入元数据（供引用校验复用） |
| 代码 | 按自然段落处理，标注 `content_type=code`，不套用列表/表格切分规则 |
| 图片 | M0 不 OCR、不向量化；生成占位符 `[图片：图N｜上下文：前后段落摘要]`；题注/alt 文本作为检索文本入库；OCR 留 M3+ |

### 3.2 结构预处理

1. 解析 plaintext，识别标题层级（章/节/条/款/项），构建**章-节嵌套列表**；
2. 读取法规**时效描述**（如"2021年1月1日起施行"），写入元数据 `effective_date`；
3. 目录若存在，M0 仅记录其章节路径，用于生成端展示导航，不影响分块。

### 3.3 递归分块流程（核心）

```
输入：章内节列表
1. 计算节长度列表 [len1, len2, ...]
2. 检出超长节（> L_child）
3. 对每个超长节判断内容类型：
   a. 含"不应被截断的列表"（分点条款/表格）
      → 列表截断 + 补充表头描述 + 每部分标"续上表/续下表"
   b. 否则
      → 自然段落切分 → 自然句切分 → 硬切分（递归降级）
4. 切分后，相邻太短的节/片段合并
5. 维护父子索引（子检索 → 命中召回父）
6. 去重（同 parent 多 child 命中时合并；相同文本块去重）
```

**超长节定义**：节文本 token 数 > `L_child`。

**递归降级顺序**（每级都选**最接近中点**的合法切分点，不设距离阈值）：
1. 自然段落边界（选最接近中点的段落分界）；
2. 自然句边界（句号/分号等，避开书名号内部；选最接近中点的句界）；
3. 硬切分（按 L_child 均分，优先在标点处断）。

**均分原则**：当需要切成 N 块时，每块目标长度 = 总长/N，允许 ±20% 波动；不追求"每块恰好 ≤ L_child"。

### 3.4 长度参数（已确认 Q3）

| 参数 | 值 | 说明 |
|------|-----|------|
| L_child | **512 token** | bge-base-zh 最大输入长度 |
| child overlap | 50 token | 实际切分目标 = 512 - 50 = 462 token |
| 短块合并阈值 | < 128 token | 相邻短块合并，合并后 ≤ 512 token |
| parent | 不设硬上限 | 完整节/表格/分点条款组 |

> 实现要求：用 bge-base-zh 的 tokenizer 精确计算 token 数，不以字符数代替。K=500 字符仅作粗略估算参考。

### 3.5 列表/表格截断与首部保留（已确认 Q4/Q5）

**分点条款示例**：

> 原文：第三十八条 有下列情形之一的，人民法院应当认定……：（一）……；（二）……；……（十）……。

若整条 10 个分点总体超长，切成 2 个 child 即不超长，则按中点（约第 6 个分点处）切分：

```
child1: 第三十八条 有下列情形之一的，人民法院应当认定……：（一）……；（二）……；……（六）……
child2: 第三十八条 有下列情形之一的，人民法院应当认定……：（七）……；……（十）……
```

每个 child 都携带**首部引导语**（"第X条 + 引导句"），保证检索到任一块都能理解其所属条款语义；**只有单个分点本身超长时，才单独为该分点切分**。

**表格**：

- 解析时线性化为文本：`表头：…；行1：…；行2：…`（或 Markdown 表格原样保留）；
- 小表格（≤ L_child）：独立成一个 child，**完整保留表头+全部行**；
- 大表格：按行切分，**每个 child 重复表头** + N 行（N 使该 child ≤ L_child）；
- 每个表格分块末尾标"续下表"，后续分块标"续上表"；
- 父片段 = 完整表格，命中子块召回完整表格展示。

### 3.6 父子索引（已确认 Q3/Q4）

- **parent**：完整节 / 完整表格 / 完整分点条款组；写入 Qdrant（`chunk_level=parent`），用于展示与生成上下文；
- **child**：检索单元（目标 512 token），写入 Qdrant（`chunk_level=child`），用于检索匹配；
- **映射**：child 携带 `parent_chunk_id`；parent 携带 `child_chunk_ids`；
- **召回**：检索命中 child → 返回其 parent（若同 parent 多个 child 命中，合并去重后返回一次 parent）；
- **邻接**：child 携带 `prev_chunk_id` / `next_chunk_id`（供前端上下文扩展）。

### 3.7 嵌入与索引构建

| 项 | 设计 |
|----|------|
| dense | bge-base-zh（768d），本地编码 |
| sparse | jieba + 内置法律词典（`experiments/data/legal_dict.txt`）→ BM25 稀疏向量 |
| collection | 沿用 `chunks`（公共库 + 用户库 + 案例库共 collection，metadata 隔离） |
| 写入 | Qdrant upsert，dense on_disk，20k 以上自动 HNSW |
| 确定性 id | `doc_id = sha256:<hash>`，`chunk_id = chunk:<16hex>`（沿用 RAG1.0 规则） |

### 3.8 元数据与 payload index（已确认 Q6）

**通用元数据**（所有 corpus 共用）：

| 字段 | 说明 | payload index |
|------|------|:---:|
| corpus | public / user / case | ✅ |
| user_id | 用户库归属 | ✅ |
| kb_id | 知识库 id | ✅ |
| law_name | 法规名（用户库为文件名） | ✅ |
| article_no | 条文号 | ✅ |
| effect_level | 效力级别 | ✅ |
| status | 现行有效/已修订/已废止 | ✅ |
| doc_type | 文档类型 | ✅ |
| parent_chunk_id | 父文档 id | ✅ |
| chunk_level | parent / child | ✅ |
| heading_path | 结构路径（章/节） | 否 |
| content_type | text/table/code/image_placeholder | 否 |
| version | 法规版本 | 否 |
| effective_date | 施行日期 | 否 |

**法律库专属**：SQLite `law_meta` 表维护法规级元数据（法规名、时效、版本、status、来源 url、发布部门、发布日期、实施日期、章-节结构树）；检索时按需 join 补充过滤条件。

### 3.9 增量更新（已确认 Q7 不涉及其他模型索引）

- 其他模型索引（qdrant_bge-m3 等）**保留不动**，本项目只用 bge-base-zh 索引；
- 增量更新流程（启动时后台执行）：
  1. 拉取国家法律库最新文件元数据；
  2. 与本地 `law_meta` + manifest 比对，识别新增/修订/废止；
  3. 变化文件 → 解析 → 分块 → 嵌入 → upsert；删除文件 → 按 doc_id 删旧索引；
  4. 更新 `law_meta` 与 manifest；
  5. 前台展示进度；失败不影响主功能，下次启动重试。
- **前置条件**：现有 manifest `files` 为空，重建索引时用 `IncrementalIndexer.rebuild_full()` 生成完整 manifest，此后增量可用。

### 3.10 用户知识库（已确认 Q8）

- 与公共库**同一套通用管线**：解析 → 分块 → 父子索引 → 嵌入 → 入库；
- 写入同 collection，`corpus=user` + `user_id` + `kb_id`；
- 用户文档同样生成 parent/child；合同条款号识别增强列入 M1+。

## 5. 验收标准

### 5.1 分块质量（人工抽检 50 个节/条款）

- [ ] 单个"条"不被切碎（分点条款除外，分点条款每个 child 必须含首部引导语）；
- [ ] 大表格每个 child 含表头，且有续上表/续下表标记；
- [ ] 相邻短块已合并，无 < 128 token 的孤立 child（除非该节本身 < 128 token）；
- [ ] 无重复 child（相同 chunk_id 或相同文本）；
- [ ] 父子映射完整：无孤儿 child，无空 parent。

### 5.2 索引构建

- [ ] 重建后索引可加载，dense+sparse 双路可检索；
- [ ] payload index 按 §3.8 建立；
- [ ] 全部 child 目标长度 ≤ 512 token（tokenizer 精确计算）。

### 5.3 增量更新

- [ ] `rebuild_full()` 后 manifest 完整；
- [ ] 模拟新增/修改/删除各 1 份法规文件，索引正确同步；
- [ ] 删除后检索不再命中该 doc_id 的任何 chunk。

### 5.4 检索基线（重建后首测）

- [ ] 重建索引在 QA_dataset/法律 上首测，作为 M0 新基线；
- [ ] 若 Recall@10 < 0.75 或 Recall@20 < 0.90，需做分块归因并给出改进方案（因为旧索引为 0.823/0.944）。

## 6. 依赖与风险

| 项 | 说明 |
|----|------|
| Markitdown docx 保真度 | 标题层级/表格可能丢失，需在 W1 用真实法规 docx 验证；失败降级 python-docx |
| tokenizer 准确性 | 必须用 bge-base-zh tokenizer 计算 token，避免超限 |
| 分点条款识别 | 需可靠识别"（一）（二）（三）"与引导句边界；识别错误会破坏首部保留 |
| 表格线性化格式 | 影响检索与展示；格式需在 W1 用真实表格样例验证 |
| PreFilter 误杀 | 不属于本模块；D02 处理（评测集补充"不应拦截"样本，M0 阈值保守） |
| 重建耗时 | 7,339 chunks 规模重建预计分钟级，可接受；若未来全量法规库扩大需评估 |
