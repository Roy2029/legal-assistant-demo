## 3. Skill 正式定义（YAML 结构）

### 3.1 存储位置

```
skills/
├─ <skill_id>/
│   ├─ SKILL.md          # frontmatter(YAML) + Markdown 正文
│   ├─ rules.jsonl       # 复杂规则库（子 Agent 加载，可选）
│   └─ templates/        # 文书/报告模板（可选）
```

### 3.2 SKILL.md 结构（YAML frontmatter + Markdown 正文）

```markdown
---
skill_id: contract_review_owner   # 唯一 id
name: 合同审查（甲方视角）
version: 0.1.0
status: runnable                  # stub | runnable | usable | good（见 §4）
input_schema:
  type: object
  properties:
    file_id: {type: string}
    review_position: {type: string, default: 甲方}
  required: [file_id]
visible_tools: [review_contract]  # 主 Agent 可见的顶级工具（D05 §4.1）
steps:                            # 可选：声明则确定性编排；不声明则 LLM 依据正文规划
  - id: review
    tool: review_contract
    params: {file_id: "{{input.file_id}}"}
  - id: human_review
    type: human_review
    params: {deliverable: report}
---

# 合同审查（甲方视角）

## 流程
1. 解析上传的施工合同文件；
2. 调用 review_contract 工具审查；
3. 生成审查报告并交用户确认。

## 决策思路
- 站在建设单位（甲方）立场，重点关注结算支付、变更签证、工期；
- 审查维度：效力与资质、价款、工期、变更签证、结算支付、质量保修、优先受偿权、违约与争议解决；
- 每个风险点必须给出：条款位置、风险等级、风险说明、修改建议、法条依据。

## 失败处理
- 文件解析失败：提示格式不支持，转人工；
- 无规则命中：返回"未发现明显风险点，建议人工复核"。

## 免责声明
本报告由 AI 生成，不构成正式法律意见，使用前须经执业律师核阅。
```

**分工原则**：
- **frontmatter（YAML）**：只保留机器必需字段（skill_id/name/version/status/input_schema/visible_tools/steps）。由工程师/框架维护；
- **正文（Markdown）**：流程、决策思路、失败处理、注意事项、免责声明——**律师/法务用自然语言编写**，框架将正文作为 LLM 的 skill 指令注入上下文；
- **rules.jsonl**：保持结构化（规则引擎需要确定性 pattern 匹配，不适合自然语言）。

**约束**：
- `visible_tools` 与 `steps.tool` 只允许引用**主 Agent 可见的顶级工具**（D05 §4.1）；
- 执行层工具不出现于 SKILL.md；
- 正文中的"失败处理"与 frontmatter `steps` 的失败降级保持一致；
- `status` 由验收流程升级（占位→能跑→能用→好用）。

### 3.3 Skill 注册表

- 启动时扫描 `skills/*/SKILL.md`，解析 frontmatter 校验结构后注册，正文一并载入；
- 前端业务动作列表由注册表动态生成（D04/D05 已约定）；
- 同一 skill 多版本共存时，注册表取最高 status 版本为默认。

## 4. Skill 生命周期（Q6）

| 状态 | 含义 | 升级条件 |
|------|------|----------|
| stub（占位） | 流程桩：工具真实调用，decision/analyze 简化 | M0 验收：流程走通、trace 完整 |
| runnable（能跑） | 流程完整，输出格式正确，无规则库或少量示例规则 | M0 验收：工具调用成功率 ≥ 95% |
| usable（能用） | 有规则库，真实文件可用率达标 | M1 验收：20 份合同前两档 ≥ 70% |
| good（好用） | 批注模式、体验优化、规则库迭代 | M3 验收：主观满意度 ≥ 4/5 |

## 5. 规则库结构（rules.jsonl，Q1）

复杂规则库独立于 YAML，由子 Agent（review_agent）加载：

```jsonl
{"rule_id": "cr-001", "dimension": "结算支付", "trigger": {"patterns": ["逾期审核", "视为认可", "送审价"]}, "risk_level": "high", "risk_desc": "逾期审核视为认可送审价对甲方极为不利", "suggestion_template": "删除'逾期视为认可'表述，改为'以双方书面确认为准'", "basis": [{"law": "建工司法解释一", "article": "第21条"}], "source": "法务朋友口述", "status": "active"}
```

**字段**：

| 字段 | 说明 |
|------|------|
| rule_id | 规则唯一 id |
| dimension | 审查维度（§7） |
| trigger | 触发条件：patterns（文本特征词）+ 可选 clause_type |
| risk_level | high / medium / low |
| risk_desc | 风险说明（模板化） |
| suggestion_template | 修改建议模板 |
| basis | 法条/示范文本依据数组 |
| source | 规则来源（法条/示范文本/法务口述） |
| status | active / disabled |

**规则引擎**：review_agent 加载规则库 → 对合同条款文本做 pattern 匹配 → 命中规则生成风险条目 → LLM 基于 risk_desc + suggestion_template 生成完整审查意见（不自由发挥）。

## 6. 首个深度 Skill：建设工程施工合同审查（甲方视角）

### 6.1 审查维度（Q2，待法务朋友核验）

| # | 维度 | 甲方核心关切 |
|---|------|--------------|
| 1 | 效力与资质 | 应招标未招标、承包人资质、转包/违法分包/挂靠、阴阳合同 |
| 2 | 价款 | 计价方式（固定总价/单价/可调）、调价机制、风险范围、垫资与利息 |
| 3 | 工期 | 开竣工日期、工期顺延程序、逾期索赔失权条款、误期违约金 |
| 4 | 变更签证 | 签证权限收口、金额上限、逾期答复视为认可（排除） |
| 5 | 结算支付 | 结算程序、逾期审核视为认可（删除）、以送审价为准（删除）、逾期付款利息 |
| 6 | 质量保修 | 质量标准、隐蔽工程验收、缺陷责任期与保修期区分、质保金返还 |
| 7 | 优先受偿权 | 行使期限（18个月）、放弃/限制承诺效力 |
| 8 | 违约与争议解决 | 违约金上限、管辖（工程所在地专属管辖）、仲裁条款有效性 |

### 6.2 规则来源优先级（Q4）

提炼规则时按以下优先级：
1. **建工司法解释一（法释〔2020〕25号）+ 民法典合同编建设工程合同章**——强制性效力规则；
2. **GF-2017-0201 示范文本**——结构性比对基准（缺失条款检测 + 通用/专用条款差异）；
3. **法务朋友口述经验**——甲方实务中的高频风险点与修改话术。

### 6.3 首版规则规模（Q3）

- M1 首版：每维度 **5-10 条**，合计约 **40-80 条**；
- 高优先级维度（结算支付、变更签证、工期）先行；
- 每条规则必须由法务朋友确认后方可入 `rules.jsonl`。

### 6.4 与 review_agent 的接口

```
主 Agent ──(review_contract)──> review_agent
  输入: {file_id, review_position: 甲方}
  内部: file_parser → 条款识别 → 规则匹配（rules.jsonl）→ 缺失条款比对（GF-2017 结构）
        → LLM 生成风险条目（基于模板）→ 报告组装
  输出: {report_id, risks:[{clause, risk_level, analysis, suggestion, basis}], summary}
```

## 7. 评测集设计（Q5）

### 7.1 评测数据

- **20 份脱敏施工合同**（建设单位/法务朋友提供，隐去当事人、金额、项目名）；
- 覆盖：总价/单价/可调价三种计价、有无逾期失权条款、有无签证限制、有无"逾期视为认可"等高风险条款。

### 7.2 评测方式

- 法务朋友对每份输出按三档打分：
  - **A 直接可用**：风险点覆盖完整，修改建议可直接采用；
  - **B 需少量修改**：需微调但主风险已覆盖；
  - **C 不可用**：漏掉高风险点或建议错误；
- **M1 验收目标：A+B 占比 ≥ 70%**；
- 评测报告关联 `rag_config_version`（D03），可复现。

### 7.3 badcase 联动

- 每份评测记录未命中风险点 → 生成 badcase 条目（D03 表），按"规则缺失 / pattern 未命中 / LLM 生成质量问题"归因；
- 归因结果驱动 rules.jsonl 迭代。

## 8. 法务朋友协作方式

| 阶段 | 协作动作 | 产出 |
|------|----------|------|
| 规则提炼（M1 前） | 每周 1 小时结构化访谈：逐维度过审查要点 | 每维度 5-10 条规则草稿 |
| 规则确认 | 法务朋友逐条审 rules.jsonl（basis 引用、风险描述、修改建议） | 确认/修订后的规则库 |
| 评测 | 对 20 份合同输出打分 | 评测报告 + badcase |
| 迭代 | 每月回顾 badcase 与新增规则 | rules.jsonl v1.x |

**访谈方法**：不问"这个 skill 好不好"，问"你审一份施工合同，从第一页到最后一页看哪些点？每个点怎么判断风险？"把回答填入规则库模板。

## 9. 版本阶梯

| 版本 | 能力 |
|------|------|
| M0 能跑 | 4 个业务动作桩（stub/runnable）：流程走通、trace 完整；review_agent 用 3-5 条示例规则 |
| M1 能用 | 首个深度 skill 上线：8 维度规则库（40-80 条）+ 评测集验收 A+B ≥ 70% |
| M2 可控 | skill 验收标准固化；评测集扩充；规则命中率/漏检率基线 |
| M3 好用 | 2-3 个深度 skill；批注模式；体验优化 |
| M4 生产级 | skill 开发 SOP 固化：访谈→规则库→评测→上线流程标准化 |

## 11. 依赖与风险

| 项 | 说明 |
|----|------|
| 法务朋友时间 | 规则提炼与评测的瓶颈；每周固定 1 小时 + 异步留言 |
| 规则库质量 | pattern 匹配可能漏检；LLM 生成部分需模板约束，防自由发挥 |
| 脱敏合同获取 | 20 份脱敏合同的可得性影响评测；M1 前必须到位 |
| 维度偏差 | 8 维度可能未覆盖建工全部风险；以法务朋友确认结果为准，可增删 |
| 甲方视角局限 | 首版只做甲方；乙方/中立视角后续扩展（skill 参数化 review_position） |
