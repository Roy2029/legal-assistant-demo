定义 **badcase 从收集到修复验证的完整闭环**：状态机、流程、优先级、与评估系统联动、各版本自动化程度。

## 2. badcase 状态机

```
new（新收集）
  → triaged（已粗分/待根因）
  → root_caused（已根因 + 修复动作明确）
  → fixed（已修复，待验证）
  → verified（验证通过，沉淀为回归用例）
  → closed（关闭）

任意节点可 → won't_fix（暂不修复，记录原因）
```

| 状态 | 含义 | 责任人 |
|------|------|--------|
| new | 用户提交 | 系统自动入库 |
| triaged | 用户粗分类完成（D03 §5.1） | 用户现场 |
| root_caused | 工程师根因 + 修复动作（D03 §5.3） | 工程师 |
| fixed | 修复已提交 | 工程师 |
| verified | 回归验证通过 | 工程师/自动 |
| closed | 关闭归档 | 系统 |
| won't_fix | 暂不修复 | 工程师 |

---

## 3. 闭环流程（五步）

```
1. 收集：前端"标记错误" / "引用有误"入口（D03 §5.1）
        ↓ 自动带 trace_id，落 badcases 表
2. 归因：工程师根因分类 + 修复动作（D03 §5.3）
        ↓
3. 修复：按根因分派到对应层——
        · 检索失败 → 词典/分块/元数据/rerank 参数（D01/D02）
        · 生成幻觉 → 引用校验器规则/Prompt（D02 §7）
        · 流程误拦 → PreFilter/解析器/难度规则（D02 §3/§4）
        · 体验问题 → 前端/输出格式
        ↓
4. 验证：修复后跑两条线——
        · 单点验证：该 badcase 复现不再发生
        · 回归验证：QA_dataset/法律 检索评估 + 200 条引用可验证率（D03）
        ↓
5. 沉淀：验证通过的 badcase 转为回归用例，加入评估集（§5）
```

---

## 4. 优先级规则

| 优先级 | 判据 | 响应 |
|--------|------|------|
| P0 | 引用错误（编造法条） | 24h 内修复 |
| P1 | 检索失败（漏召回/误召回）且高发（同根因 ≥ 3 条） | 当周修复 |
| P2 | 流程误拦（PreFilter/解析器） | 纳入最近迭代 |
| P3 | 体验问题 | Backlog 排期 |

---

## 5. 与评估系统的联动

- **badcase → 回归用例**：`verified` 状态的 badcase，其 query + 期望结果（根因修复后人工确认）沉淀为回归用例，加入 `QA_dataset/法律` 的补充集（真实问题集，Backlog P0）；
- **回归用例来源分层**：
  - 合成 qrels（现有 2,254 条）：检索基线；
  - 真实 badcase 回归集（M2 起）：质量底线；
  - 律师真实问题集（M2 起）：覆盖真实分布；
- **评估报告**（D03 §4.3）必须包含：badcase 修复数、回归通过数、真实问题集表现。

---

## 6. 各版本自动化程度

| 版本 | 能力 |
|------|------|
| M0 能跑 | 收集入口可用；badcases 表 + 手动导出；工程师手动归因（演练 1 轮） |
| M1 能用 | badcase 列表 UI（状态筛选/优先级）；修复-验证手动关联 |
| M2 可控 | 自动化归因脚本（按 D03 §5.3 根因规则分类）；badcase 回归集接入评估；效果量化 |
| M3 好用 | 每周自动汇总根因分布；修复效果自动对比；badcase 看板 |
| M4 生产级 | badcase 数据驱动持续优化机制固化；评估基准版本化发布 |

---

## 7. 验收标准

- [ ] 前端两处收集入口可用，数据落 `badcases` 表并自动关联 trace_id；
- [ ] 状态机字段完整，流转记录（状态变更历史）可查；
- [ ] M0 演练：用 demo 期间收集的律师反馈走完 1 轮"收集→归因→修复→验证→关闭"；
- [ ] 至少 3 条 badcase 沉淀为回归用例（M2 前以文件形式保存）。

---

## 8. 依赖与风险

| 项 | 说明 |
|----|------|
| badcase 数量不足 | demo 阶段用户少，样本少；M0 用内部测试 + 法务朋友反馈补量 |
| 归因依赖人工 | M0/M1 工程师手动归因；M2 自动化脚本需按 D03 根因规则训练/编写 |
| 修复验证成本 | 每次修复跑全量评估耗时；M1 起只跑受影响子集 + 全量周跑 |
| 状态机纪律 | 状态流转不严会导致闭环断掉；M1 提供 UI 约束 |
