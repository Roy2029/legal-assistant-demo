# 法律助手 Demo 第二步行动计划（PLAN）

> 版本：v0.1
> 目的：定义"第二步——分阶段逐个模块细化设计"的协作方式、文档集结构与行动顺序
> 前序：第一步（资料盘点与思路对齐）已基本完成，资产索引见 INVENTORY_*.md

---

## 1. 版本路线（总纲）

持续开发、持续交付，按五个能力台阶推进：

| 版本 | 主题 | 一句话目标 | 对应关系 |
|------|------|-----------|----------|
| M0 | 能跑 | 全链路走通，demo 可演示 | 原 ROADMAP 6 周排期 |
| M1 | 能用 | 核心功能完整，律师可日常使用 | M0 后迭代 |
| M2 | 可控 | 质量可度量、可回溯、可迭代 | 评估/观测/badcase 闭环生效 |
| M3 | 好用 | 体验、速度、成本达到专业工具标准 | 打磨优化 |
| M4 | 生产级 | 安全、合规、稳定性、交付标准化 | 正式交付 |

原则：**每个版本都是一个可交付的完整应用**，不是"先做一半再补另一半"。

## 2. 功能线 × 版本阶梯

四条纵向功能线 + 三条横向能力线：

| 功能线 | 代号 | M0 能跑 | M1 能用 | M2 可控 | M3 好用 | M4 生产级 |
|--------|------|---------|---------|---------|---------|-----------|
| 知识库问答（RAG） | F1 | 混合检索+rerank+引用校验闭环 | 用户知识库、词典、法条号精确检索 | 评估集回归、检索质量达标 | 速度优化、结果解释增强 | 分块策略终版、增量更新稳定 |
| 智能体基础 | F2 | LangGraph 主从骨架、流式、会话 | ReAct loop、工具系统、会话管理、上下文压缩 | 全链路 trace、工具调用可审计 | 交互体验、错误恢复 | 稳定性、并发、资源占用 |
| 子 Agent | F3 | 知识库 agent、案例 agent（离线库）、文书 agent 桩 | 联网搜索 agent（agent reach skill）、案例 MCP 可选 | 各 agent 独立评估 | agent 间协作优化 | 子 agent 可插拔、可升级 |
| 实务 skill | F4 | 业务动作桩（4 个入口） | 1 个深度 skill（建工合同审查·甲方视角） | skill 验收标准与评测集 | 2-3 个深度 skill | skill 开发 SOP 固化 |
| 可观测性（横） | X1 | Trace 面板 + Langfuse 埋点 | 全链路 trace 可读 | 检索/工具/生成全指标 | trace 性能分析 | 审计级可追溯 |
| 评估系统（横） | X2 | qrels 回归可跑 | 引用可验证率 100% 接入 CI | 真实问题集 + badcase 集 | 自动评估报告 | 评估基准版本化 |
| badcase 闭环（横） | X3 | 手动收集 | 前端"标记错误"入口 | badcase 归因分类 | 迭代闭环流程化 | 数据驱动持续优化 |

部分模块走"占位符 → 能跑 → 能用 → 好用"的内部升级路线，按版本时机安排迭代：

| 模块 | M0 | M1 | M2 | M3+ |
|------|-----|-----|-----|------|
| 脱敏 | 规则版（正则） | 规则版+开关 | 规则版+badcase 补规则 | 本地小模型 NER |
| PDF 解析 | Markitdown 直转 | docx 降级链 | 双栏/页眉页脚专项处理 | OCR/扫描件 |

| Router/Planner | 关闭 | 关闭 | badcase 归因后重评 | 选择性激活或废弃 |

## 3. 文档集结构

```
docs/
├─ SPEC.md                  # 总体规格（持续修订，是所有设计的"宪法"）
├─ ROADMAP.md               # 版本路线（M0-M4，持续更新）
├─ PLAN.md                  # 本文件：第二步行动计划
├─ INVENTORY_MCP.md         # 资产索引（第一步产出）
├─ INVENTORY_RAG1.0.md      # 资产索引（第一步产出）
└─ designs/                 # 模块细化设计（第二步起增量产出）
    ├─ D01-RAG-离线索引构建.md
    ├─ D02-RAG-在线检索生成.md
    ├─ D03-RAG-可观测性与评估.md
    ├─ D04-Agent-基础框架.md
    ├─ D05-Agent-子Agent与工具系统.md
    ├─ D06-实务Skill-框架与首个Skill.md
    ├─ D07-安全脱敏与文件解析升级路线.md
    ├─ D08-badcase收集与迭代闭环.md

```

每份设计文档统一结构：

```
1. 目标与边界
2. 现状（资产/代码/已知坑）
3. 模块设计（架构、接口、数据流）
4. 版本阶梯（占位符-能跑-能用-好用，逐级定义）
5. 验收标准
6. 依赖与风险
7. 开放问题
```

## 4. 行动顺序（细化设计会话）

按依赖关系排序，每个会话产出一份设计文档，并**增量修订 SPEC / ROADMAP**：

| 会话 | 主题 | 产出 | 前置 |
|------|------|------|------|
| A | 版本路线与模块边界对齐 | PLAN.md（本文）+ ROADMAP v0.3 | 第一步完成（已满足） |
| B | RAG 离线索引构建 | designs/D01 | A |
| C | RAG 在线检索生成 | designs/D02 | B |
| D | RAG 可观测性与评估 | designs/D03 | C（可并行于 B） |
| E | Agent 基础框架 | designs/D04 | A |
| F | 子 Agent 与工具系统 | designs/D05 | E |
| G | 实务 Skill 框架与首个 Skill | designs/D06 | E、F |
| H | 安全脱敏与文件解析升级路线 | designs/D07 | A |
| I | badcase 收集与迭代闭环 | designs/D08 | D |
| J | 整体 review | 修订全部文档 + 交付开发 | B-I 完成 |

每个会话的讨论方式：
1. 我先基于现有资产与 SPEC 提出该模块的**设计问题清单**；
2. 你逐项确认/修正/补充；
3. 我落笔写设计文档初稿；
4. 你 review 后定稿，并同步修订 SPEC/ROADMAP 受影响部分。

## 5. 协作规则

1. **文档即代码**：所有设计决策必须落入 docs/ 下的文件，讨论结论不留在对话里；
2. **增量修订**：每次细化设计后，检查 SPEC/ROADMAP 是否需要同步更新，保持文档一致性；
3. **ADR 记录不可逆决策**：涉及选型、范围裁剪、架构取舍的决策，写 ADR-*.md；
4. **先设计后开发**：每个模块必须完成对应设计文档并通过 review，才进入开发；
5. **版本阶梯是验收标准**：每个模块在设计文档中明确"M0/M1/M2/M3 各做到什么程度"，开发按阶梯交付。
